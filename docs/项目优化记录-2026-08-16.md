### 一、后端 Bug（3 个，由代码审查发现，全部修复并通过测试）

#### BUG-B1（高）系列延展提案引用 `LLMClient` 不存在的属性，AI 可用时必然 500

- **文件**：`backend/app/services/content_opportunity.py`（约 L745）
- **问题代码（修复前）**：

  ```python
  model_identifier=(
      self.llm.providers[self.llm.active_provider].model
      if proposal_source == "ai" and self.llm
      else None
  ),
  ```

- **根因**：`LLMClient` 的真实属性只有 `settings / model / capabilities / timeout /
  client / _max_retries`，根本不存在 `providers` 和 `active_provider`。这段代码是
  按早期多 provider 设计写的，重构为 OpenAI 兼容单端点后未同步。
- **触发条件**：配置了可用 LLM 后，任何走 `proposal_source == "ai"` 路径的
  系列延展机会提案。
- **影响**：必然抛 `AttributeError` → 接口 500，AI 提案功能完全不可用；
  当前本地未配置 LLM 所以只走手动路径，问题被掩盖。
- **修复方式**：改为引用真实属性 `self.llm.model`。
- **验证**：`tests/services/test_creator_series.py` 中 FakeLLM 原先也迎合 buggy 接口
  写着 `providers/active_provider`，同步改为 `model = "test-model-v1"`；该文件
  L543 的既有断言 `model_identifier == "test-model-v1"` 恰好成为本修复的回归测试。
  全量后端测试通过。

#### BUG-B2（中高）文件数据库每个新连接的外键约束与 busy_timeout 全部失效

- **文件**：`backend/app/core/database.py`
- **问题代码（修复前）**：`init_db` 在借用的**单个**连接上执行
  `PRAGMA foreign_keys=ON` 与 `PRAGMA busy_timeout=5000`。
- **根因**：SQLite 的 PRAGMA 是**每连接**生效的。文件型数据库使用 `NullPool`
  （每次操作新开物理连接），之后每个新连接都是 `foreign_keys=OFF`、
  `busy_timeout=0`。测试用 `:memory:` + `StaticPool`（全程同一连接）完全掩盖了该问题。
- **影响**：
  1. 生产路径外键约束形同虚设，可写入孤儿记录（如素材指向不存在的用户），
     数据完整性依赖应用层自律；
  2. 无 busy_timeout 时并发写入遇锁立即抛 `database is locked`，而非等待重试。
- **修复方式**：改用 SQLAlchemy 的 connect 事件监听器，在每个新连接建立时重放 PRAGMA：

  ```python
  @event.listens_for(self.engine.sync_engine, "connect")
  def _set_per_connection_pragmas(dbapi_connection, connection_record):
      dbapi_connection.execute("PRAGMA foreign_keys=ON")
      dbapi_connection.execute("PRAGMA busy_timeout=5000")
  ```

- **验证**：新增回归测试类 `TestPerConnectionPragmas`（`backend/tests/core/test_database.py`）：
  - `test_file_db_fresh_connection_keeps_pragmas`：文件 DB 新连接上
    `foreign_keys==1`、`busy_timeout==5000`（注意该 PRAGMA 返回列名为 `timeout`）；
  - `test_file_db_foreign_key_violation_rejected`：文件 DB 上插入孤儿记录确实抛
    `IntegrityError`（修复前此操作会静默成功）。

#### BUG-B3（中）创作者规则确认接口并发竞态，败者请求污染 `active_version_id`

- **文件**：`backend/app/services/creator_rule.py`（`decide()`）
- **问题代码（修复前）**：`decide()` 用 UPDATE 把 `proposed` 版本置为激活，
  但**不检查受影响行数**。
- **根因**：状态预检在事务外执行，两个并发确认请求可能都通过预检；先提交者
  完成激活后，后提交者的 UPDATE 匹配 0 行却继续执行，把 `active_version_id`
  指向一个并未激活的版本。姊妹服务 `creator_viewpoint / creator_series / evidence`
  均有 rowcount 检查，此处遗漏。
- **影响**：并发确认（双击、多端同时操作）下激活指针错乱，用户看到的
  "当前生效规则"与实际激活版本不一致。
- **修复方式**：UPDATE 增加 `AND status='proposed'` 条件后检查
  `updated.rowcount != 1`，为 0 时抛 `VersionConflictException`（即本次请求
  在竞态中落败，不得触碰 `active_version_id`）。
- **验证**：既有的并发/版本冲突测试全部通过；全量后端测试通过。

### 二、前端 Bug（4 个，已修复并经逐项审核验证）

#### BUG-F1（高）素材删除"影响确认"流程完全失效

- **文件**：`frontend/src/services/api/client.ts`（根因，parseResponse 非 ok 分支）、
  `frontend/src/pages/Materials/MaterialsPage.tsx`（L151-159）
- **问题代码（修复前）**：

  ```ts
  // client.ts：非 ok 响应只保留 message，丢弃了响应体中的 meta/details
  const error = new Error(message) as Error & { response?: { status: number; data?: { message?: string } } };
  error.response = { status: response.status, data: { message } };
  ```

  ```ts
  // MaterialsPage.tsx：依赖 err.response.data.meta.details.projects 展示影响列表
  const affected = response?.data?.meta?.details?.projects?.map((item) => item.title) || [];
  if (affected.length) setDeleteImpact(...); else setError(...);
  ```

- **触发条件**：删除任何被项目引用的素材。后端返回 409 `MaterialInUseException`，
  响应体 `meta.details = { projects: [{id,title}], confirmation_required: true }`
  （已在 `backend/app/core/exceptions.py`、`backend/app/services/material.py` 中确认）。
- **用户可见影响**：确认 UI（"将影响：… / 保留引用快照并删除"）永远不出现，
  被项目引用的素材永远无法删除，用户只看到通用错误提示。
- **修复方式**：`parseResponse` 的错误分支保留完整响应体 `meta`，挂到
  `error.response.data.meta`，MaterialsPage 无需改动即可读到 `details.projects`。
- **验证**：浏览器实测——创建素材并关联项目后点击删除，正确出现
  "将影响：{项目名}"和"保留引用快照并删除"按钮
  （截图 `docs/ux-evidence/material-delete-impact-confirmation.png`）。

#### BUG-F2（中）候选内容确认 / 复盘确认入口加载失败后永久转圈

- **文件**：`frontend/src/pages/Content/ContentPage.tsx`（IntentActionPanel）
- **问题代码（修复前）**：

  ```tsx
  useEffect(() => {
    if (/* 需要打开 human gate */) {
      void openHumanGate(action.id).then(setGate).catch(() => undefined); // 失败被吞掉
    }
  }, [action.action_type, action.id, gate, ...]);
  ```

- **触发条件**：`openHumanGate` 请求因网络抖动或后端 5xx 失败一次。`gate` 保持
  `null`，依赖数组不变，effect 不再执行，也没有任何重试入口。
- **用户可见影响**：发布前确认、复盘确认面板永久显示转圈动画，无错误提示、
  无法重试，用户被卡死。对比同文件 `PublicationForm` 已有 `gateError + 重试`
  机制，此处遗漏。
- **修复方式**：新增 `gateError` / `gateAttempt` 状态；失败时记录错误信息，
  三处 spinner（候选确认、未知结果确认、复盘确认）改为"错误提示 + 重试按钮"；
  `gateAttempt` 变化触发重试。
- **审核补充**：初版实现在 `useEffect` 内同步调用 `setGateError(null)` 触发
  `react-hooks/set-state-in-effect` lint 错误（CI 会失败），已将清错逻辑移入
  `retryGate` 事件处理器，并在加载成功的 `.then` 中清除错误态。
- **验证**：`npm run build` 通过；212 个前端测试全部通过；full lint 0 错误。

#### BUG-F3（中低）假设表单"观察窗口"可提交 NaN

- **文件**：`frontend/src/features/content/StageForms.tsx`（HypothesisForm）
- **问题代码（修复前）**：

  ```tsx
  onChange={(event) => setObservationWindow(Number(event.target.value))}
  disabled={... || observationWindow < 1 || observationWindow > 365}
  ```

- **触发条件**：在数字输入框输入 `-`、`1e` 等中间态时 `Number()` 得到 `NaN`；
  NaN 与任何数值比较都为 false，禁用条件失效。清空输入安全
  （`Number('') === 0` 会被 `< 1` 拦住）。
- **用户可见影响**：`observation_window_days: NaN` 经 JSON.stringify 变为 `null`
  提交，后端收到非法值（422 报错或写入异常），用户困惑。
- **修复方式**：状态改为保存原始字符串，禁用条件增加
  `Number.isNaN(Number(observationWindow))` 守卫，提交时统一 `Number()` 转换。
- **验证**：构建 + 全量测试通过。

#### BUG-F4（中）内容页幂等键每次点击重新生成，与全站已统一模式不一致

- **文件**：`frontend/src/pages/Content/ContentPage.tsx`、
  `frontend/src/features/content/StageForms.tsx`
- **问题代码（修复前）**：

  ```ts
  const makeKey = (prefix: string) => `${prefix}-${Date.now()}-${Math.random()...}`;
  // 每次点击都生成新键，失败重试无法被服务端去重
  ```

- **触发条件**：任何创建/变更命令在"服务端已处理、响应丢失"的模糊失败后重试
  （如网络中断）。Materials/Starter/Opportunities/GrowthOnboarding 四个页面在
  上一轮审计中已统一为"失败重试复用同键、成功后轮换"，ContentPage 遗漏。
- **用户可见影响**：重试可能重复创建项目/内容版本（无版本守卫的操作），
  或触发令人困惑的 409 版本冲突。
- **修复方式**：
  1. ContentPage 新增 `keyCacheRef + stableKey(signature)`：同一签名复用同一键；
  2. `runCommand` 增加可选第二参数 `idempotencyKey`，命令**成功后**删除缓存键完成轮换；
  3. `StageAction` 与各 StageForms 组件的 `onCommand` 类型同步扩展，11 处调用点传入签名；
  4. `ProjectCreateForm` 等组件改收 `stableKey`。
- **审核补充**：已核实该"失败复用同键"模式与后端语义匹配——后端 replay 记录与
  业务写入处于同一事务，失败的请求不会留下 replay 记录，因此重试复用同键安全。
- **验证**：构建 + 212 个前端测试全部通过（含既有的幂等键复用/轮换测试）；
  浏览器实测双击创建项目仅产生 1 个项目。

## 第二部分：走查发现的 26 项体验问题（已全部修复）

> 以下问题来自两轮以新用户身份的完整走查：注册 → 今日首页 → 新手流程 →
> 创建内容项目 → 工作台逐段确认 → 素材管理 → 机会 → 我的，含边界操作
> （不存在的项目 URL、全空表单提交、短密码等）。

### 高优先级（影响核心流程或造成明显困惑，7 项）

#### UX-H1 两字中文姓名被注册表单拦截，无自定义引导

- **现象**：注册页"姓名"最少 3 字符，输入"小明"被浏览器**原生**校验拦截
  （"请将该文本增加为 3 个字符或更多"），文案未本地化。
- **影响**：目标用户是中文创作者，两字姓名（小明、李华、王芳）非常常见，
  注册第一步即受阻。
- **建议**：姓名最小长度改为 2，或按语言区分；补充中文自定义校验提示。
- **截图**：`register-name-blocked.png`、`register-name-invalid.png`

#### UX-H2 今日首页 AI 依据区显示英文枚举 `content_seed`

- **现象**：首页推荐依据直接展示原始枚举字符串 `content_seed`。
- **影响**：普通用户无法理解，显得产品未完成。
- **建议**：建立枚举到中文文案的映射（如 `content_seed → "选题灵感"`）。
- **截图**：`home-today-page.png`

#### UX-H3 候选内容"依据"显示原始 UUID

- **现象**：项目工作台候选内容的依据字段直接展示
  `1206f6f5-xxxx-...` 形式的 UUID。
- **影响**：依据本应帮助用户判断候选质量，原始 ID 无任何信息量。
- **建议**：依据应解析为对应素材/证据的标题，解析失败时显示"内部依据记录"。
- **截图**：`project-candidate-uuid-evidence.png`

#### UX-H4 首页 AI 依据泄露 `evidence:…` 原始 ID

- **现象**：首页依据文案中出现 `evidence:1206f6f5-…` 这类内部标识。
- **影响**：与 UX-H3 同类，内部标识符暴露给终端用户。
- **建议**：展示层统一把 evidence/source 引用解析为人类可读标题。
- **截图**：`home-evidence-id-exposed.png`

#### UX-H5 我的页显示 `stable_publish` 枚举，且与成长页中文文案不一致

- **现象**：我的页"当前创作目标"（两处）显示原始枚举 `stable_publish`，
  而成长页同一概念显示中文"稳定发布"。
- **影响**：同一概念两种呈现，用户困惑；英文枚举不可读。
- **建议**：全局统一枚举→中文映射。另注意"内容策略"字段语义问题（见 UX-M9）。
- **截图**：`me-page-stable-publish.png`

#### UX-H6 新手评估提交后莫名跳转机会页，流程迷失

- **现象**：新手流程（Starter）评估步骤提交后，用户被带到机会页而非
  下一步引导，没有过渡说明。
- **影响**：新用户不知道发生了什么、接下来该做什么，容易流失。
- **建议**：提交后显示明确的进度反馈（"评估完成，接下来…"）再引导跳转。
- **截图**：`starter-step1-assessment.png`

#### UX-H7 "生成内容机会"点击后无任何反馈

- **现象**：机会页点击"生成内容机会"后界面无 loading、无 toast、无状态变化
  （在未配置 LLM 的降级环境下尤其明显）。
- **影响**：用户以为按钮坏了，反复点击。
- **建议**：点击后立即给出加载态；降级环境下明确提示原因与替代路径。
- **截图**：`opportunities-empty-state.png`
