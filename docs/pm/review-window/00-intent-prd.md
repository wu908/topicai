## 1. 问题与证据（绑基线 commit 与行号）

- **现象**：`frontend/src/pages/Review/ReviewPage.tsx:43`（基线 `ce7be40`）`const rows = await listWeekly(60);`——一次拉 60 天；同文件 `:69` 副标题与 `:92-93` 左栏标题写「本周对照 {compared.length}」；`:54-55` 的 `compared` 只按 `stage !== 'needs_snapshot'` 过滤，无日期再切分。
- **产品定义**：`docs/ai-native-async-creation-plan-2026-08-29.md:24` 原文「**周度批确认**：每周一次、一屏对照本周全部已发内容的判断 vs 实际，逐条确认结论或标"未知"」。
- **后端**：`backend/app/api/v2/async_loop.py:150` `days: int = 7`；服务层 `backend/app/services/weekly_review.py:19-20` 同为 `days: int = 7`，`_since` 为**滚动窗口** `now - days`（`:128-130`），非自然周。
- **歧义记录**：`docs/reviews/feature-inventory.md:1639-1642`（J9）与 `:2131`（A9 表）已把「周复盘 7 天 vs 60 天」列为待决；条目内行号已过期（实际 `ReviewPage.tsx:43` / `async_loop.py:150`），本次一并修正。
- **影响**：用户看到的「本周对照」混入最多 60 天数据，按周理解不成立；后续「复盘完成率 / 周对照」类度量分子分母不同窗口（注：该类度量目前无现行实现，属未来口径问题）。

## 2. 目标用户与场景

- 目标用户：已发布内容、需要回填表现数据并做周度复盘的创作者。
- 场景：打开 `/review` → 左「本周对照」（**近 7 天**发布的已对照内容）+ 右「欠对账」（**≤60 天**仍待回填的内容）+ 公式笔记。
- 用户价值：本周视图只含本周；超过一周的待回填仍有入口，不会丢。
