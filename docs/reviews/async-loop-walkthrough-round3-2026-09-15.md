## 三、实走发现的其余问题

1. **【已修 #111】** 发布按钮灰着不解释原因（见上）。
2. **【已定位并修复，2026-09-15】原判断"状态间歇性丢失"是误判**——真相是**首屏慢时的中间态没有文案**。
   - 复现方式（确定性）：只把 `publish-checks/latest` 延迟 3 秒，其余请求正常；或用 CDP 把 CPU 降速 6 倍。
   - 用组件内埋点拿到的完整序列：`render → render → effect start → cleanup → effect start`，
     **没有 `fetched`、也没有请求事件**——也就是说状态从未被丢弃，是请求还没回来；
     把等待从 4.5 秒加到 15 秒，同一降速条件下 6/6 全部正常。
   - 我当时把"结果还没到"读成了"结果丢了"（冷启动 Vite 首次编译，首屏就是慢）。
   - 真正的缺陷是：这段时间界面显示「先运行发布前检查」——等于告诉用户"你没跑过"，
     于是他会去重复点「运行检查」，或以为发布按钮坏了。
   - 修法：区分三态（有结果 / **正在读取** / 确实没有）。实测：延迟期间显示「正在读取检查结果…」，
     结果到达后变「可以发布」。
3. **【产品判断，留给下一轮】solve 类的两个必填项消化器不产出**：「读者遇到什么问题」
   「你准备给出的答案」。草稿正文里其实已经回答了它们（"我的读者不是来看结论的，而是想看你当时
   怎么想的"），但系统不代填，用户必须自己写。这可能是**有意**的（发布意图是用户的判断），
   也可能是消化器该多产出一项——我倾向后者（能显著减少一次填写），但这是产品口味，先不动。
4. **【方法记录】** 两个走查坑：主内容是内部滚动容器，`fullPage` 截图拍不到折叠线以下（我因此
   一度误判悬浮球压住按钮，命中测试证明毫无重叠）；IAB 后台标签 rAF 被节流 → Playwright 的
   元素稳定性检查永不通过 → **点击与截图都会超时**，这不是产品问题。另外我差点误报"确认已发布
   一直禁用"，实际是我的脚本在检查状态加载完成前就读了 `isEnabled`——**截图救了这一次**。

## 五、验收基准（本轮新增）

- 拾取面板默认视图：读者变化字段预填该产出的草案，认领可用，意图预选值等于产出的 `content_intent`
- 认领后：`content_versions ≥ 1`、`material_usages ≥ 1`、草稿正文与产出一致
- 认领后的下一步动作是 `review_candidate`（而非 `answer_key_question`）
- 源素材缺失时仍能认领（少一条溯源，不失败）
- 发布前检查未取到结果时，必须显示"先运行发布前检查"
