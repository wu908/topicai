## 1. 结论摘要

被测产品的**主链路是通的**：注册 → 丢素材 → 消化生产 → 拾取 → 内容项目 → 逐段确认 → 悬浮球对话，AI 全部真实可用，`AI 只提议、人确认` 的产品原则在绝大多数界面被正确执行。

但存在 **3 个阻塞级问题**，其中任何一个都足以让用户在第一次使用时判定「这东西坏了」。问题集中在三类：**承诺与交付不一致**、**控件语义误导**、**状态与文案自相矛盾**。

| 严重度 | 数量 | 用户可感知后果 |
|---|---|---|
| 🔴 阻塞级 | 3 | 用户按提示操作后得到完全不同的结果，怀疑产品失效 |
| 🟠 高 | 3 | 用户困惑/误操作，需反复试错才能继续 |
| 🟡 中 | 15 | 体验粗糙、信息不可扫读、可发现性差（含移动端 F26/F27；F5 由「高」降级至此） |
| ⚪ 低 | 8 | 细节不一致（可访问性、文案标点、截断、路由别名） |

## 3. 🔴 阻塞级问题

### F1 — 急稿承诺「三步十分钟见成品」，实际交付一个 0/5 步的新项目

**位置**：`/urgent`

页面头部写「**三步，十分钟内见成品**」，主按钮写「**生成成品，进入发布检查**」。用户填完三步、选择 `让它判断`、点击该按钮后：

- 实际跳转到 `/content/{新项目id}`；
- 项目处于「准备中」，进度 **0/5 步**；
- 界面显示「先把这篇的目的定下来」，并开始生成目的方向候选。

**用户感受**：我说好了要成品，你却给了我一个刚开头、还要我确认 5 个步骤的空项目。

**根因方向**：`急稿` 的承诺文案与 `POST /api/v2/projects` + 异步循环的接线不匹配——按钮文案描述的是「同步产出成品」，实际执行的是「创建一个待走完整闭环的项目」。二者必须对齐（要么改文案与预期，要么真的先产出候选内容）。

**建议**：`急稿` 应当复用 S15 已被验证良好的「AI 先推断 + 单个追问」模式，并且在产出候选内容之后再承诺「进入发布检查」；在此之前按钮应写明「创建项目并让 AI 准备候选」。

### F2 — 逐段确认承诺「替换」，但替换入口被藏在「拒绝」之后，且已被接受的段落无法编辑

**位置**：`/content/:projectId`，`[data-testid="candidate-segment"]`

界面原文：「你可以保留、拒绝或**替换**任意一段。」

实测三种状态：

| 段落状态 | 可用控件 |
|---|---|
| `pending`（待确认） | `确认保留`、`拒绝这一段` —— **没有替换** |
| `accepted`（已保留） | `重新修改这一段` —— 点击后**只把状态退回 pending，不出现任何输入框**（无 textarea、无 input） |
| `rejected`（需替换） | 才出现 `替换这一段` 文本框 + `提交替换内容` |

**问题**：
1. 承诺的「替换」在用户看到承诺的那一屏**根本不存在**，必须先点「拒绝」才会出现——与文案并列的三选项实际是两步操作；
2. `重新修改这一段` 的命名暗示「可编辑」，实际是「撤销确认」，**误导性强**；
3. 已确认段落无法直接改写正文，只能撤销后重走拒绝路径。

**建议**：`pending` 状态直接并列三键（保留 / 替换 / 拒绝）；`accepted` 状态提供真正的就地编辑；把「重新修改」改名为「撤销确认」，或直接实现编辑。

### F25 — 参考锚失败时把 Pydantic 原始报错吐给用户，并清空用户已粘贴的输入

**位置**：`/onboarding/reference`（「贴参考，读出你想做成什么样」）

**复现**：在「参考内容」粘贴 2 条参考（`@账号名` + 标题 + 正文）→ 点「读这些参考」→ 等待约 20 秒。

> **间歇性说明（第三轮补测修正）**：同日以同一路径重试，**同一条链路成功返回**，未复现该报错。
> 因此 F25 **不是必现**，它取决于模型是否返回 schema 合法的结构化输出。
> 但**缺陷本身与是否复现无关**：只要结构化输出连续 3 次校验失败、且降级路径也产出非法数据，用户就一定会看到原始报错且输入被清空。后端日志已完整记录该因果链，属确定性代码路径。
> 对照成功那次的输出质量：系统主动丢弃了模型 6 处无法与参考对上的依据（`limitations: ["模型给出的 6 处依据对不上你的参考，已丢弃——只保留有据可查的结论"]`）——**这条降级逻辑做得很好，恰恰说明失败路径的体验反差太大**。

**界面实际显示**（截图 `browser-screenshots/finding-F25-pydantic-leak.png`）：

```
1 validation error for _AnchorDraft topics List should have at least 1 item after
validation, not 0 [type=too_short, input_value=[], input_type=list]
For further information visit https://errors.pydantic.dev/2.10/v/too_short
```

这是**逐字透出的后端 Pydantic 校验错误**。对一位中文创作者而言，它同时暴露了内部模型名（`_AnchorDraft`）、字段名（`topics`）、约束（`at least 1 item`）、以及一个 pydantic 官方文档链接，且全是英文。

**后端日志还原的完整因果链**（`backend/app/services/reference_anchor.py:237`）：

1. LLM 返回的结构化输出不合规：`audience` 字段返回了**字符串**而不是 `_DraftItem` 对象；
2. `app/core/llm.py:126` 校验失败 → 重试（日志 `Invalid structured LLM output; retrying` ×2）；
3. 3 次后仍失败 → 抛 `LLMStructuredOutputException` → 日志 `Reference anchor read failed; falling back`；
4. **但「降级」路径自己产出了非法数据**（`topics: []`），再次触发校验失败；
5. 该异常未被翻译，直接成为 `GET /api/v2/reference-anchor` 的 **400** 响应体，前端原样渲染。

**三个叠加缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| F25a | 原始校验错误直接进 UI | 用户看到一个无法理解、无法行动的英文技术报错 |
| F25b | **失败后用户粘贴的内容被清空** | 用户白贴一次，必须重新输入——这是数据丢失，不是展示问题 |
| F25b | 失败后**看不出参考是否已存下** | 导入已成功落库、输入框按设计清空，但用户只看到空框 + 英文报错，无法分辨是否白贴了一次（性质是「不可知」，非数据丢失） |
| ~~F25c~~ | ~~「重试」只关掉横幅、不会重试~~ | **撤销**：实测 `重试` 调用的就是 `load()`，确实会重新发起读数；当时「点了没用」是因为后端降级必失败 |
| F25d | 「重试」按钮文字**竖排折行**成「重 / 试」 | 横幅布局在窄高度下挤压按钮，属排版缺陷（见截图右侧） |
| F25e | 「降级」不是降级 | 声称 fallback，实际 fallback 产出非法数据并转为 400，用户无任何可恢复路径 |

**建议**：
1. 所有校验/异常在 API 边界翻译为面向用户的中文文案（保留英文技术细节到日志/`meta`，不进 `message`）；
2. 失败时**保留用户输入**，并把「重试」改为真正的重试（用同一份输入重跑），或改名「关闭」；
3. 修复 fallback：降级路径必须产出通过自身 schema 的数据，或在无法产出时给出「暂时读不出，可先跳过」的显式出路；
4. 给 `_AnchorDraft` 这类内部模型名一个对外别名，禁止出现在任何用户可见文本里。

#### ✅ F25 修复记录（2026-09-19）

**真实根因**（比首轮判断更精确）：前端 `parseReferences` 给每条参考都写 `tags: []`，
于是「参考没有标签」是**常态而非例外**。后端降级读法 `_read_deterministically` 只从标签
词频推选题，没有标签时构造出 `topics=[]` 的 `_AnchorDraft`，撞上 `min_length=1` 抛
`pydantic.ValidationError`。该异常继承自 `ValueError` → 命中 `exceptions.py` 的
`value_error_handler` → 非生产环境下 `message = str(exc)` 原样返回。
**降级路径自己抛错，等于没有降级。**

> **兼两处更正（首轮判断有误）**：
> 1. 首轮说「重试按钮只关掉横幅、不会重试」**是错的**——`ReferenceAnchorPage.tsx:185`
>    的 `重试` 调用的就是 `load()`，它确实会重新发起读数。此前观察到「点了没用」是因为
>    后端降级必失败，重试必然再次 400。**后端修好后重试路径即恢复**，故 F25c 撤销。
> 2. 首轮说「用户输入丢失」需限定：导入（`POST /reference-imports`）**已经成功落库**，
>    输入框是在导入成功后按设计清空的，随后只有「重读」这一步失败。数据没丢，但
>    **用户看到空输入框 + 一串英文报错，无法分辨自己是不是白贴了一次**——这是真问题，只是性质是「不可知」而非「丢失」。
>
> 另：该原始报错是**开发环境特有**（生产分支会把它替换成「请求参数无效」）。但底层故障
> （降级产出非法数据 → 400）在所有环境都会发生，生产用户会撞上一个无出路的 400。

**改动**（5 个文件，+201 / −14）：

| 文件 | 改动 |
|---|---|
| `backend/app/services/reference_anchor.py` | 降级读法在无标签时改用**参考标题**（用户自己贴的、可数也可核对的信号），并保证任何情况下都返回**合法**草稿 |
| `backend/tests/services/test_reference_anchor.py` | +2 用例：无标签降级返回合法读数、降级不向调用方泄漏校验异常（**修复前两条均红**） |
| `backend/tests/api/v2/test_reference_anchor_api.py` | +1 用例：无标签参考走 HTTP 返回 200 而非 400，且 `message` 不含 `pydantic` / `_AnchorDraft` |
| `frontend/src/pages/Onboarding/ReferenceAnchorPage.tsx` | 读数失败时明说「你贴的参考已经存下了，点重试只重新读一次，不用重新粘贴」；`重试` 加 `whiteSpace: nowrap` + `flexShrink: 0` 修掉竖排折行；helperText 补「多条之间空一行」（F28） |
| `frontend/src/pages/Onboarding/__tests__/ReferenceAnchorPage.test.tsx` | +2 用例：已存下提示、重试真的重新发起读数 |

**门禁结果**：后端 `530 passed`，覆盖率 **90.43%**（门禁 80%；`reference_anchor.py` 单文件 98%）；
前端 `290 passed / 44 files`，`lint` 与 `build` 均通过。

**同时关闭**：F25b（已存下却看不出来）、F25d（按钮折行）、F28（分隔规则未说明）。
**F25c 撤销**（原判断有误）。

### F26 — 「更多」面板是半透明底却没有毛玻璃，底层文字直接透出

**位置**：`≤720px` 移动端底栏的「更多」面板（`.v3-more-sheet`）

```css

  background: var(--v3-sidebar-bg);      /* rgba(255,255,255,0.55) —— 只有 55% 不透明 */
  border-top: 1px solid var(--v3-border);
  box-shadow: 0 -12px 30px rgba(70, 95, 130, 0.12);
```

实测计算样式：`background: rgba(255,255,255,0.55)`，**`backdropFilter: none`**。

**建议**：补 `backdrop-filter: blur(...) saturate(...)`（与全站玻璃一致），或改用不透明底 `--v3-surface-solid`。

## 7. 做得好的地方（重构时务必保留）

以下模式在本轮测试中表现优秀，是产品真正的差异化，重构内容页时**不应被推翻**：

1. **「AI 先推断 → 单点追问 → 可一键否决」**（`/content` 新建项目、S15）。实测：一句模糊想法 → AI 推断出「教方法」并给出理由 → 提供 `不对，我自己选` → 只问一个最关键的缺料问题。这是全站体验最好的流程。
2. **逐段确认 + 拒绝后才替换** 背后的产品原则（不覆盖已确认版本、不自动发布）表达得很清楚，只有控件组织需要改。
3. **空态文案质量高**：收件箱、周复盘、机会、素材的空态都明确说明「为什么空」与「下一步做什么」。
4. **AI 方向候选 + `换一批`**：给 3 个带理由的方向，用户可以点选后随意改，完全符合「AI 只提议」。
5. **π 形灯框 + 独立输入泡**的对话形态与 `DESIGN.md` §6 定稿一致，视觉完成度高。
6. **主链路真的能用**：从零注册到产出候选内容，全程无需人工干预，AI 是真实调用的。
7. **参考锚会主动丢弃模型编造的依据**（三轮补测新发现）：成功那次返回 `limitations: ["模型给出的 6 处依据对不上你的参考，已丢弃——只保留有据可查的结论"]`，并把每条结论标注为「只有 1 条参考这么说 / 这条由 1 条参考得出，只是观察，不代表规律」，每条还配一个「不对」按钮。**这是全站最强的反幻觉设计**，也正好说明 F25 的失败路径体验反差有多大。
8. **引导实验（`/onboarding/assessment`）把格式要求说在了前面**：提交按钮禁用时直接写明「至少填写一条你亲自经历过的内容、愿意探索的兴趣或会做的事，才能继续」——对比收件箱的 `丢进去` 禁用时毫无说明，这里是对的做法。其 AI 生成的三条方向**只来自用户刚填写的内容**，并显式声明「不依赖热点或流量预测」。
9. **参考页的解析结果实时回显**（`已识别 N 条参考` + 阈值提示「1 条只能看出方向；再贴 1 条才看得出规律」）：解析器的设计意图就是「不让用户学格式，而是让他确认我们读对了」。虽然分隔规则未写进提示（F28），但这个回显机制本身值得保留并推广。
