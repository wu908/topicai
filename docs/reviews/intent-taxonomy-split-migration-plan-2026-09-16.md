# 迁移方案：把「内容是什么」与「机器做什么」拆开（2026-09-16）

> 触发：用户连问三次——「内容意图为什么是三个枚举」「这样不会导致内容的局限吗」「只有三个枚举会把 AI 的产出局限在三个类型里吧」。
> 结论：**枚举本身不是问题，问题是一个字段在同时干两件事**；删除枚举是错的解法，加法（新增开放字段 + 把枚举正名为行为键）才是对的。
> 本文是分步方案：每一步一个 PR、可单独回退、**每一步之后线上都可用**。

---

## 一、问题陈述（先说清"为什么必须动"）

`content_intent` 今天同时承担两件事：

1. **机器行为**：状态机分支（`_derive_action`）、发布假设要哪些必填字段（solve→读者困境/你的答案、share→视角锚点、record→持续承诺）、发布后观察哪些信号、复盘用哪套读者反应词；
2. **"这是什么内容"的标签**：卡片上的「解决内容/分享内容/记录内容」、工作台那句「这条内容要让读者理解你的经历、观点或感受」、确认面板让你在下拉里选一个。

两个后果都是真实的：

- **用户被要求在一个描述内容的字段上做机器建模**（原始抱怨「内容意图就三个选项，我根本看不懂」）；
- **意图判断错了会改变"哪些已沉淀经验被用上"**——`content_genome.py:147`：

  ```python
  if query["content_intent"] and applicability["intent"] != query["content_intent"]:
      continue        # 这条规则不适用于这一篇
  ```

  也就是说它不是装饰性字段：#124（意图改为读内容判断）之前，粘一段文字会被判成 `solve`，于是"为 share 沉淀的经验"不会被引用。判断错 → 用不上对的经验，而且用户完全看不出来。

## 二、为什么"删掉枚举"是错的解法

发布假设的必填字段、信号词表、规则适用性匹配，都需要一个**可比较的有限键**。把自由文本当路由键，等于把"理解它到底属于哪一类"这件事推给每一个消费方（12 个文件、139 处引用），而且每处都会各自解释一遍、互相不一致。

所以正确的判断是：**枚举用在"机器行为"上是对的，用在"描述内容是什么"上是错的**——要拆，不是要删。

## 三、目标模型

| | 内容形态 `content_form` | 机器行为（沿用 `content_intent`） |
|---|---|---|
| 取值 | **开放**：作品展示 / 教程 / 清单 / 观点 / 复盘 / 对比 / 故事…由 AI 命名 | **有限三值**：solve / share / record |
| 来源 | 模型读内容给出（可改） | 模型判断 + 用户一次点击确认 |
| 作用 | 只用于**展示**与**提示词上下文** | 路由、必填字段、信号词表、规则适用性 |
| 用户是否要选 | 否 | 是（但已预填、一次点击） |

关键点：**AI 从此可以给内容起任意精准的名字，而机器仍然只在有限维度上分支**。用户不再看到"从三个里选一个"。

## 四、现状清点（实测，不是估计）

- **引用**：139 处 / 12 个文件。最多三处：`content_genome.py` 30、`content_opportunity.py` 17、`intent_actions.py` 11。
- **带 CHECK 的表**（若要**加第四种行为**才需要动）：
  `020_intent_driven_actions`（两处：content_projects 等）、`023_creator_rule_versions`、
  `025_creator_viewpoints`、`026_creator_series`、`027_content_opportunities`；
  `050_async_creation_loop` 的 deliverables 为**可空** CHECK。
  → 六张表要重建。**这就是"不为了内容形态动 CHECK"的理由**：形态走新增开放列，是纯加法。
- **前端用户可见处**（5 处）：内容列表/工作台的 `projectIntentLabel`、确认面板的意图下拉、`ObservationList` 的规则说明、`SeriesPanel`、`UrgentPage`。
- **E2E**：`grep` 确认**没有任何 E2E 断言意图标签文案**（只断言内容词），所以文案改动风险比预想小。
- **ADR 0002**：历史内容的发布意图保持 NULL，`intent_status` 才是判据——新增字段不得破坏这条。

## 五、分步（每步一个 PR）

### Step 1 · 加字段（纯管道，零视觉变化）
- 消化器在判断草案里**再加一个 `content_form`**（自由文本，≤20 字，明确要求具体、不要"日常分享"这类含糊词）；`#124` 已经让它同时给出 `content_intent`。
- `deliverables` 与 `content_projects` 各加 `content_form TEXT`（可空）。
  **迁移陷阱（已踩过两次）**：`content_projects` 的 intent 重建迁移会把**旧表所有列原样拷进新表**，新列必须**同时**加进 `043` 的重建 DDL 常量，否则迁移直接失败。
- 认领时把形态一并交给项目（与 `#109` 的交接同一处）。
- **前端完全不读它** → 线上零视觉变化。
- **回退**：两列留着不用，行为与今天逐字节相同。

### Step 2 · 展示层换位（本步才有视觉变化）
- 产出架卡片、内容列表、工作台那句「这条内容要让读者理解…」改为**先显示 AI 命名的形态**（没有形态时回落到现在按意图的标签）。
- 确认面板文案从「确认这是一条"分享"内容吗」改为**「这篇要读者拿走什么」**，下拉仍保留（它现在是行为键），但说明改为「AI 判断为…；不对就改」。
- **回退**：单个 PR 还原渲染。

### Step 3 · 把行为键正名为"机器模式"
- rubric 里三条的 `label` 从内容分类词（解决/分享/记录）改为**判定需求的描述**（教方法 / 讲经历 / 记过程），并让 `content_genome` 的规则适用性匹配继续挂在这三值上——**它的语义本来就是"这类判定需求"**，只是名字一直被当作内容分类读。
- 不改数据库。

### Step 4 · 仅当真的出现第四种**行为**时
- 加 rubric 条目 + 一次迁移放宽那六张表的 CHECK（逐表重建、逐表可回退）。
- **不再为了"内容形态"动 CHECK**——那时形态已经在开放字段里了。

## 六、验收基准

- 新产出：`content_form` 非空、来自模型、与内容相称（抽查 10 条，人工判断"这名字对不对"）
- 界面：不再出现"从三个里选一个"的步骤；形态由 AI 给出、可改
- **行为不变**：状态机分支、发布假设必填字段、信号词表、规则适用性过滤的语义全部保持（全量回归 + 现有 E2E 全绿）
- 每一步之后线上可用；每一步可单独回退且**无数据破坏**（只新增列、不改写既有列）

## 七、明确不做

1. **不把行为键改成自由文本**（会把解释推给 12 个消费方）；
2. 不在这一步引入**用户自定义 rubric**（需要配额、版本、审核，属另一阶段）；
3. 不改 ADR 0002 的历史内容语义（`intent_status` 仍是判据，`content_intent` 仍可为 NULL）。

## 八、风险

| 风险 | 处置 |
|---|---|
| 新列未同步进 `043` 重建 DDL → 迁移失败 | 已列入 Step 1 的必做项；重建 DDL 常量里已有注释说明这条规律 |
| 模型给出的形态名含糊（"日常分享"） | 提示词要求具体且 ≤20 字；UI 可改；抽查验收 |
| 形态字段被下游误当路由键 | 一条测试守：形态参与展示与提示词，**不参与**任何路由/匹配判断 |
| 三值行为键将来仍不够用 | Step 4 预留了加法路径；但那时是"新增行为"，不是"新增内容形态" |
